# Problem

DIN provider endpoints are not intended to be secret information. We intend for them to be published on smart contracts in the medium term, and in the short term it is convenient to share Caddyfile configs without having to worry about keeping API keys secret. But if the DIN endpoints are made public, we need to be able to stop unauthorized users from making large volumes of requests.

This document lays out a simple handshake between the DIN router and DIN providers, which is backed by a Caddy implementation on both sides.

# Goals

Over the medium to long term, we want to have payments between DIN Gateways and DIN Providers handled by the proxies. We want the transition process for DIN Providers to feel like a simple upgrade to the software we are putting in place now, and thus we try to anticipate what information the eventual payments protocol will need and rely on those same pieces of information to keep the transition smooth.

# Configuration

In the initial implementation of the authentication protocol, the bare minimum configuration requires:

## DIN Router

- A Web3 EOA private key to sign requests
- The existing configuration mapping services to provider endpoints

## DIN Provider

- A whitelist of Web3 Addresses to accept requests from
- A secret key to create signed session tokens (this is shared across all Caddy instances run by the same provider)
- A configuration mapping services to backend endpoints (this allows providers to run one set of DIN Provider Proxies for an arbitrary number of services).

# Protocol

1. For each service / provider pairing, the DIN Router establishes a session.
   1. The DIN Router sends an EIP-4361 authenticated message to the DIN Provider at `https://$PROVIDER_ENDPOINT/auth`.

      The Sign In With Ethereum message has the form:

      ```
      Message: $MESSAGE
      $DOMAIN wants you to sign in with your Ethereum account:
      $SIGNER_ADDRESS

      URI: $PROVIDER_URL/auth
      Version: 1
      Chain ID: 1
      Nonce: $NONCE
      Issued At: $ISSUED_AT
      Expiration Time: $EXPIRE_TIME
      ```

      - `$MESSAGE`: At this time, the contents of this field are not important. Within the Sign In With Ethereum protocol, this is intended to be shown to the user signing with a wallet. As these signatures are automated, this field can be ignored, but is included by Sign In With Ethereum libraries.
      - `$DOMAIN`: Domain reflects the address of the router.
      - `$SIGNER_ADDRESS`: Matches the address used to sign this message.
      - `$PROVIDER_URL`: Matches the public address of the provider verifying this message.
      - `$NONCE`: A random value specified by the signer to distinguish this request from others.
      - `$ISSUED_AT`: An ISO-8601 Timestamp of when this message is created
      - `$EXPIRE_TIME`: An ISO-8601 Timestamp of when this message should no longer be accepted. Note that this is not the expiration of the token being requested, just for this request. It is generally within a few minutes.

      This message is included in a JSON payload of the form:

      ```json
      {
        "msg": "Message: ... Expiration Time...",
        "sig": "0x12234...0abcd"
      }
      ```

      Where `sig` is the signature produced by signing the message with the private key associated with `$SIGNER_ADDRESS`.

2. The DIN Provider verifies the message and confirms that the signer appears in its whitelist.
   - If the message does not verify or the signer is not in the whitelist, the DIN provider responds with a 401 status code.

3. The DIN Provider responds with:

   ```json
   {
     "headers": {"x-api-key": "$API_KEY"},
     "exp": $EXPIRATION_TIME,
     "uses": $USES_LIMIT,
     "error": "$ERROR_MESSAGE"
   }
   ```

   - `$API_KEY`: The API key generated by the provider.
   - `$EXPIRATION_TIME`: A Unix timestamp after which this key is no longer accepted. Either this or `uses` is specified, not both.
   - `$USES_LIMIT`: The number of times this key may be used. Either this or `exp` is specified, not both.
   - `$ERROR_MESSAGE`: A message indicating why the other fields could not be provided.

4. For each request to the DIN Router:
   1. The DIN Router selects a provider that offers the service capable of handling the incoming request.
   2. If there is a current API Key available for that service / provider pairing, the router forwards the RPC request to that provider including the API Key associated with the session in the `x-api-key` header.
      - If there is not a current API key for that service / provider pairing, the DIN Router establishes a session as defined above.
   3. The DIN Provider verifies the API key in the `x-api-key` header and ensures that it is associated with the appropriate service.
      - If the API key is not present, the provider responds with a 401 status code.
      - If the API key is present but is expired or does not authorize access to the requested service, the provider responds with a 403 status code.
      - If the API key verifies successfully, the provider proxies the request to the backend service and returns the response.

# Implementation Notes

The following details are pertain to the DIN Caddy implementation of the authentication protocol, but are not considered a part of the protocol itself. These details may change in the future as the project evolves.

* All session tokens are issued with a 1 hour expiration timeline.
* The gateway will automatically renew that token shortly before its expiration.
* Each gateway instance establishes its own sessions, and session tokens are not shared across instances.
* The session API keys issued by the DIN Caddy proxy are JWT tokens that are HMAC authenticated for quick verification without the need for a shared session store. Clients should treat the session keys as opaque strings, and not rely on inspecting the JWT object.
